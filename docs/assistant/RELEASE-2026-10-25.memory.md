# Portal worker memory optimization — 2026-10-25

This is a memory-only maintenance release. The existing two browser sessions, one per provider, compute plan `1c-2g`, pricing, search queues and OTP flow remain unchanged. No parallel-session pool or paid infrastructure is introduced.

## Changes

- Before asking Chromium to capture a preview, inspect the trusted body's bounds with a one-second timeout. Withhold the preview when bounds are absent, non-finite, non-positive, exceed 4096 CSS pixels on either dimension or exceed four million CSS pixels in area. Do not alter the supplier DOM. Previously the 500KB encoded JPEG check happened after the bitmap had already been allocated.
- Keep metadata updates every three seconds. For an unchanged job and stage, attempt the expensive JPEG capture at most once per ten seconds. New job/stage transitions can capture immediately. Metadata-only updates carry the server's already accepted image without renewing its original timestamp. The worker retains only a small receipt, never a second JPEG copy. Authentication, passenger entry, failures, job changes and shutdown still withhold stale images.
- Bind the Air Arabia login-response diagnostic once per page per adapter via a WeakSet. Reusing the named login page no longer accumulates a new response listener on every sign-in. Other listeners and existing origin checks are preserved.

## Validation

718 automated tests pass. Focused tests cover preview size guards before capture, cadence, accepted-image carry and expiry, sensitive-stage clearing, publishing failures, unchanged quote outcomes, reused-page sign-in and existing listeners.

An offline real Chromium comparison used synthetic trusted-origin HTML with no supplier login or customer data. During a simulated 60-second unchanged normal scene, captures decreased from 21 to 6 while metadata publications remained 21. A 1280 by 10000 body was captured three times by the previous code and zero times after the preflight guard. These are capture-work measurements, not a claim of a 71% RAM reduction. Browser RSS could not be read reliably in the local runtime, so no local RSS reduction is claimed.

The live pre-release 30-minute Render sample (2026-10-25 01:57:15–02:27:15 UTC) had 30 memory observations: median 1,629,564,900 bytes, p95 2,013,323,300 bytes, peak 2,076,446,700 bytes against a 2,147,483,600-byte limit. Background work was active. Compare post-release samples under representative work; a lower reading immediately after browser restart cannot establish the sustained saving caused by this patch.

## Release

Publish the same worker source to main and the independent combined-worker branch, then deploy only `airarabia-portal-keepalive`. Verify both provider authentication/protected refreshes, accepted preview events, continued quote/catalog work and post-deploy memory. Render process status alone is not proof of an authenticated session. Hotel services and web-service configuration are outside this maintenance change.
