# Bounded background searches and Air Arabia idle browser lifecycle

The combined worker remains running for supplier pricing. It must not be suspended merely because Gmail OTP is available. The web and worker compute plans remain unchanged; no additional browser, parallel lane, paid resource, booking or hotel-system change is introduced.

## Behavior

- Background catalog work may start at most two jobs per provider per fifteen-minute window. Starts, including failed or abandoned work, consume the persisted budget. Window rollover does not create catch-up bursts. Customer requests retain priority and do not consume this budget. Existing catalog coverage and freshness limitations still apply.
- With the existing queue and Gmail OTP configuration enabled, the Air Arabia browser closes after three minutes of genuine idle time. The Node process keeps polling. A queue-authenticated, read-only demand probe never claims work, spends catalog budget or marks a dormant provider ready. An active customer job or catalog lease pins the browser awake, including an ambiguous completion response.
- Real eligible demand reopens the existing Air Arabia runtime and verifies authentication before a lease can be claimed. Login, OTP handling, protected refresh checks and quote calculations use the existing implementation. Authentication challenges or failed cleanup block further automatic opens rather than creating a login loop or overlapping browsers.
- FlyCham stays warm because its configured verification path is manual. Gmail availability for Air Arabia is not evidence of automatic FlyCham verification. The staff monitor distinguishes a deliberately dormant browser from authenticated readiness and clears old previews.
- The first request after a cold period may need additional sign-in time. Running Render is not proof that either supplier session is authenticated.
