# Ahmed consultant release — 2026-10-23.4

This release is for the independent flight WhatsApp assistant only. It does not change the hotel system, issue tickets, create reservations, or take payments.

## Conversation

- The collection default is 35,000 ms of silence after the latest message, with the existing 180,000 ms maximum burst age and explicit-start flush. Cline and supplier response time are additional.
- Every substantive conversational turn goes through Cline understanding, including social messages, corrections, offer inquiries, and negotiation. Sensitive credential messages and explicit privacy controls stay local. Gemma remains the configured fallback; no paid OpenAI fallback is added.
- Context includes direction, party, explicit versus default baggage, return duration, geographic flexibility, selected and verified offers, semantic question state, and an expiring single expansion proposal.
- Unknown intent preserves known trip facts and requests one narrow clarification. Supported supplier operations remain bounded: one adult, SHJ–DAM and reverse. Language understanding does not expand verified supplier coverage.
- Offer inquiries and price recommendations read verified cards without selecting or booking. A selected offer may be repriced for that airline; an ordinary airline mention does not exclude comparison.
- Overlapping slow turns retain their own durable inbox entries until each succeeds. Persistent encrypted conversation storage remains enabled on the existing web disk.

## Comparison and alternatives

- A parent request owns independent provider/date child jobs. Starting FlyCham does not cancel Air Arabia; an actual customer amendment cancels the previous request revision.
- Fresh matching catalog offers may seed a comparison (15-minute per-offer freshness). Party, itinerary, dates, and baggage must match.
- Offer totals come only from authenticated worker metadata or matching verified catalog records. Supplier reply prose is never a source of price or inventory.
- Each provider has a typed status: verified offers, partial, confirmed no flights, explicitly sold out, unverified, or authentication required. Technical errors never imply sold out.
- Confirmed negative exact-date inventory triggers searches at minus/plus 1, 2, and 3 days for that provider. Fixed return dates stay fixed; an explicit stay duration shifts both dates. Past Dubai dates and invalid combinations are excluded.
- All verified timings are retained up to the existing 80-offer bound, with separate provider capacity and global option references. A partial update can be sent after 60 seconds if offers exist, followed by one final update. An 8-minute comparison deadline preserves verified offers and marks unfinished work unverified.
- Cards state airline, airports, dates, flight number, departure/arrival, baggage, final AED total, and verification time. FlyCham vouchers remain future-use gifts, never a reduction to the current fare.

## Portal reliability

- Both sessions use protected authenticated navigation after 15 idle minutes, checked every minute. Keepalive is not a flight search and never clicks Book.
- Only confirmed supplier activity refreshes health. Failed tasks do not postpone the next check. Queue readiness is withdrawn during stale health, recovery, verification, or closure.
- One bounded retry handles transient protected-navigation failure. Authentication challenges and rejected credentials stop repeated login attempts.
- FlyCham initializes its protected search form before claiming work, detects verification even if a menu header remains visible, and supports a narrow one-use private OTP file handoff for recognized trusted forms. OTP/CAPTCHA cannot be guaranteed avoidable.
- Airport selection scopes dropdown candidates, avoids wrapper matches, uses ordinary blur, and permits one bounded city-name retry only after an empty selection. The actual supplier airport code must still match.
- Failed background catalog searches back off rather than immediately repeating every three seconds.

## Release checks

The release requires the full local test suite, both-provider webhook integration, and post-live verification of the web health payload, WhatsApp connection, worker authentication/readiness, and protected-navigation events. Successful deployment alone does not prove a portal session or fare search succeeded. Live supplier selection and unobserved OTP layouts remain subject to verification after deployment.

No additional paid resources or plan upgrades are introduced by this release. A worker redeploy can require device verification; the web conversation disk does not persist the worker's browser device identity.
