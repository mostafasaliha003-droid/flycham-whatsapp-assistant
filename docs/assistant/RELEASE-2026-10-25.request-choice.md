# Current request or independent request

Version: `2026-10-25.request-choice.1`.

When a customer already has an itinerary and sends an ambiguously scoped new travel request, Ahmed offers two native WhatsApp reply buttons: `متابعة طلبي الحالي` and `طلب جديد مختلف`. The numbered text also accepts 1/2 while that exact menu is pending. A first request, a known missing-field answer, clear baggage/date amendments, quote selection, status, booking, cancellation, privacy requests and staff-owned conversations do not receive an unnecessary scope menu.

The current itinerary and supplier jobs remain intact while the customer chooses. Continue applies the held request once to the existing trip; the explicit customer choice outranks a conflicting model suggestion to queue it separately. New starts a clean itinerary without inheriting the old passengers, dates, custom baggage, airline restriction, selected offer, handoff or trip memory. If an actual customer search is running, the independent request queues behind it and receives a clean model context when started.

Pending choices are encrypted with existing assistant state and scoped by random UUID, trip and a 30-minute expiry. Stale/replayed/foreign buttons cannot reset a newer trip. A clear current-trip operation dismisses the menu, so a later bare offer number cannot accidentally act on an obsolete scope prompt. Employee ownership still suppresses automated replies. Accepted interactive messages enter the same protected conversation journal as text responses.

Transport uses the existing Graph sender and credentials, with two fixed reply buttons, no automatic fallback POST after an ambiguous outcome, and canonical action/nonce extraction from recognized button replies. Incoming button titles are not trusted as instructions.

Validation: 712 tests pass, including 64 policy cases, 14 engine cases, six signed local HTTP checks, transport/extraction checks and the full existing suite. External Cline/Meta calls in these tests are mocked. No test customer message is sent to production.

Deploy the web service only. Portal worker code, login sessions, pricing policy, plans and hotel services require no change.
