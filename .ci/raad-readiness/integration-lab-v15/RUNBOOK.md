## What the existing test mode actually guarantees

`src/raad-login-pilot/execution-policy.js` captures `RAAD_EXECUTION_MODE=non_submitting_test` once. Requests cannot override that mode, switch to production or replace bridge configuration. Test worker admission requires a separate `RAAD_TEST_JOB_BRIDGE_KEY` (different from the worker's production bridge key) and `RAAD_TEST_MAIN_URL`. Numeric `http://127.0.0.1:<port>/` is allowed; another HTTPS origin requires exact `RAAD_TEST_APPROVED_MAIN_ORIGIN`. The production main origin is rejected. An optional carried `RAAD_MAIN_URL` must equal the isolated test main, not production.

The actual worker checks current authenticated leases on the isolated main and validates case, applicant, documents, authorization and OTP challenge. Test status cannot claim saved/submitted/completed artifacts, even if an injected flow claims success. Raw browser callbacks, submission and confirmation are blocked. The browser fence blocks WebSockets, service workers, cross-origin/query action aliases and redirects rather than following them.

This is not a government sandbox. Its allowlist still permits login POST and `/SmartForm/SendOtpSms`, and allowed GETs/agreement actions are not guaranteed side-effect-free. Therefore non-submitting mode alone is insufficient authorization for real government login, legal acceptance, account access or SMS. Do not open a real portal in the owner-only transport test.

The main dispatcher has a global `RAAD_VISA_AUTOMATION_ENABLED` flag and processes pending outbox/jobs, not a shipped owner-only lab admission mode. `DRY_RUN=true` stops actual WhatsApp dispatch and the workflow treats that as not delivered. `DRY_RUN=false` enables ordinary configured deliveries; it must not be used on shared production state merely to obtain one diagnostic reply. The main's worker URL is HTTPS-only; the existing synthetic fixture uses a checked virtual origin mapped to numeric loopback. Do not weaken production URL rules for a test.

## Current achievable proof

The new portable lab supplies a one-session, sender/Meta-test-metadata/job/challenge gate and a strict loopback transport. A NEW scenario wires both to the actual main and worker routers, with real coordinator/lease/OTP HTTP contracts and synthetic Graph/portal DI. It proves one valid synthetic reply reaches the exact worker once, invalid sender/job/replay do not reach the routes, the original challenge deadline applies and submission stops at the actual test boundary. The 19 boundary tests separately cover signature, wrong phone/WABA, OTP mismatch, expiry, concurrent use, restart refusal, private/production config contamination and forbidden real transports. Four synthetic encrypted state/ledger tests cover disabled-profile recovery without restoring allowance.

The initial synthetic job is bootstrapped before the lab gate is created; the new wired scenario covers the OTP handoff rather than intake, accounting or initial dispatch. Native-challenge/expiry negative cases are boundary unit cases, not separate full-router scenarios.

This closes a local wiring gap. It does not prove real Meta webhook delivery, government SMS, portal acceptance, model accuracy or production readiness. `REAL_META_ENABLED=false` is hard-coded and no live credential loader exists.
